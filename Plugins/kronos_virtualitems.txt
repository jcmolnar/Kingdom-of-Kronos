kronos_virtualitems.dll  —  SERVER-side plugin (Phase C PROBE, READ-ONLY)
=========================================================================

STATUS: v0 PROBE. This build does NOT modify anything. It is the safe
first step of the belt-item "virtual slots" feature (make belt items show
in the VANILLA stock inventory screen). It only proves — at runtime, on a
real server — that the reverse-engineered T1Vista.exe addresses are
correct, before any datablock-push code is written.

What it does
=============
Registers ONE console command:

    vslotProbe()  -> "Sound Profile|Sound|Damage Skin|...|Item|...|IRC Channel"

It reads the 31 dataNames[] string pointers at the confirmed table address
0x0060ed44 and returns them. If the returned string starts with
"Sound Profile" and ends with "IRC Channel", every confirmed address in
T1VISTA_RE_MAP.md is proven correct at runtime and the plugin's
engine-memory read path works. Full per-index detail is written to
kronos_virtualitems.log.

It patches NO engine code, hooks NO sites, posts NO events, writes NO
engine memory. It CANNOT disconnect players or crash the server.

Install (DEV/LOCAL SERVER ONLY for now)
=============
Drop kronos_virtualitems.dll in this Plugins\ folder and add to the
$dedicated block in Plugins\Scripts\PluginLoader.cs:

    $PluginLoader::kronos_virtualitems = true;  // Phase C probe (read-only)

Restart the server. On load it logs "--- kronos_virtualitems (PROBE)
loaded ---" and "registered vslotProbe" to kronos_virtualitems.log.

Commands
=============
READ-ONLY (safe anywhere):
    vslotProbe()               -> the 31 datablock-group names (address self-test)
    vslotDbm()                 -> "sg=.. dbm=.. items=N .."  (N must == getNumItems())
    vslotPeek(hexAddr [,count]) -> dword dump (SEH-guarded; general RE tool)

WRITE (test on a DEV/LOCAL server FIRST — these POST datablock events):
    vslotResend(managerId)     -> re-send ALL datablocks to one client (connect
                                  path). managerId = that client's %clientId.
    vslotPushItem(managerId, itemIndex)
                               -> surgical: re-send ONE ItemData slot to a client
                                  (whatever description script last set on it).

GO/NO-GO PROTOCOL (dev server, one connected vanilla client, its %clientId = C):
    getItemData(5).description = "TESTXYZ";   // pick an item index you can see
    vslotPushItem(C, 5);                       // or: vslotResend(C);
Open that client's inventory: the row shows "TESTXYZ" live, no disconnect = GO.
Wrong managerId => the event is simply dropped (harmless). Watch
kronos_virtualitems.log for "event posted OK".

Verify the READ-ONLY foundation first from the server console:

    echo(vslotProbe());

EXPECTED:
    Sound Profile|Sound|Damage Skin|Armor|Static Shape|Item|Item Image|
    Moveable|Sensor|Vehicle|Flier|Tank|Hover|Projectile|Bullet|Grenade|
    Rocket|Laser|Interior Shape|Turret|Explosion|Marker|Debris|Mine|
    Target Laser|Seeking Missile|Trigger|Car|Lightning|Repair Effect|
    IRC Channel

Send that output (and kronos_virtualitems.log) back — it confirms the
foundation and unblocks writing the actual per-client push.

Why a probe first
=============
T1Vista.exe is the Borland-compiled, UNSYMBOLIZED live-server exe. The
push mechanism (DataBlockManager::sendDataToClient / DataBlockEvent +
postCurrentEvent) is precedented IN THIS EXE (PlayerManager.cpp posts
per-client events), but the remaining addresses (sg.dbm, sendDataToClient,
per-client managerId) must be resolved and VERIFIED before a DLL that
writes to the network can safely run. A wrong address = live-server crash.
This probe verifies the confirmed addresses with zero risk, on a local
server, first. See Plugins\Source\kronos_virtualitems\T1VISTA_RE_MAP.md.

STATUS 2026-07-11 — ADDRESSES DECOMP-VERIFIED; GO/NO-GO IS THE LAST STEP
===========================================================================
The whole T1Vista.exe is now decompiled (T1Vista_RE_Kit\RE\). Every address
and offset the WRITE commands (vslotResend / vslotPushItem) use was cross-
checked against the raw decomp of DataBlockManager::sendDataToClient — the
push asm is a byte-for-byte replica of one iteration of the engine's own
per-client send loop (see T1VISTA_RE_MAP.md "Address confidence — RESOLVED").
So there is NO wrong-address crash risk left. A wrong managerId is still just
a dropped event. The DLL compiles clean with build_kronos_virtualitems.bat.

The only thing left that code can't settle is EMPIRICAL: does a re-pushed
ItemData's renamed row actually render in the STOCK client's inventory, and
does the client survive the data->preload on receipt? Run the go/no-go once
on DEV to find out. It cannot crash the server whatever the result.

GO/NO-GO (dev server, one connected VANILLA client, its %clientId = C):
    // pick an item index the client can see in their inventory (e.g. 5)
    getItemData(5).description = "TESTXYZ";   // or .shownName - see below
    vslotPushItem(C, 5);                       // surgical single-row push
Open that client's inventory. Watch for:
  * The row shows "TESTXYZ" live, no disconnect  => GO. Note WHICH assignment
    (description / shownName / name) actually changed the visible text.
  * Client disconnects at push => the data->preload failed (usually a hudIcon
    bitmap the client lacks). Keep hudIcon unchanged; only rename => retry.
Log lines land in kronos_virtualitems.log ("event posted OK").
