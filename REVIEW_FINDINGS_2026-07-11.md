Full multi-agent review of every script in `rpg/scripts`, with an independent adversarial

## 0. Context for whoever fixes these — READ FIRST

Knowledge NOT visible from the code alone (it lived in the reviewer's session notes). A fresh
session needs it to avoid making things worse.

### Fix conventions (house style)
- **Debug-gate, don't delete.** Off-by-design or suspicious code is disabled behind a `$flag`, not removed.
- **Tombstone comments.** When you remove/replace something, leave a short comment saying what was there and why.
- **Respect `DESIGN DECISION` comments.** Code carrying that marker is deliberate — do not "fix" it.
- **Verify engine claims against TribesSource** (`..\TribesSource`, full engine C++). Don't guess at builtin behavior.
- **Brace-balance check every edited file** — there is no compiler to catch a stray brace; a counting/`awk` pass is the norm.
- **Language traps that ARE the bug in many findings:** `%var` is local, `$var` global; a misspelled var reads as `""`/0 silently. `== != < >` are **numeric** (all non-numeric strings compare equal as 0); `$= !$=` are string. Missing call args arrive as `""`, extras are dropped.

### Vanilla-client compatibility mandate (HARD RULE)
Unmodified Tribes clients connect to this server. Any non-stock HUD/feature MUST be gated on the
`KHudOn` handshake; the vanilla path must reproduce exact stock behavior. Chat `~category` tags go
**last** in a message and **never start with `w`** (the engine strips them so vanilla clients are safe).

### clientId / bot architecture (bears on findings #5–9, #26–29, #62–63)
- Client/player ids come from one shared pool: ids **2048–2175**, where **2048 is the reserved server slot** (never allocated), so players/bots get **2049–2175**. Wire format caps at 2175.
- That pool is shared by **three actors at once** — real players, enemy (combat) bots, and townbots — all `Player` objects. Assuming an id is "a bot" or "a player" without checking is a bug class.
- **The layered/redundant id-safety checks in `ai.cs` are DELIBERATE hardening — do not consolidate them** (hundreds of hours of stability work).
- **Townbots are immune to player damage on purpose** (anti-lag). Not a bug.

### Load order & the exec-time-schedule footgun (root cause of several findings)
- Scripts load via an `exec(...)` list in `Server.cs`. **A later definition of the same function name silently overwrites an earlier one** — across files AND within one file. This is exactly what makes finding #3 (`Vehicle::onCollision` defined twice) and the refuted `remote.cs remoteConsider` live-vs-dead. When deduping a double-defined function, keep the INTENDED copy and delete/rename the other.
- **`schedule()` loops started at raw exec time are flushed on mission load.** Periodic loops must (re)start from `Mission::init` or a watchdog (findings #26, #49, #63; refuted `advertisements.cs`). A persistent `$LoopStarted` guard never reset on mission load will *prevent* the intended restart (finding #49).

### Known-deliberate — do NOT flag or "fix" (already excluded from this report)
Townbot damage immunity; **shout distance 5** (deliberately nerfed from 60 — anti-exploit, do NOT
restore); **party-EXP overpayment** (known, owner deferred — leave until asked); `DualWielding.cs`
calling undefined `GetRemort()` (known latent bug).

### Testing / deploy reality
The owner tests on a **separate live server**; edits in this folder must be **hand-copied there** —
changes here are not automatically live. Script edits take effect only when the server re-`exec`s them
(or reloads). No build step for `.cs` scripts, but load order still matters.

### 1. #porkbelly is a name-based admin backdoor open to any player
`comchat.cs:5307` — _comchat-commands, confidence: high_ **[re-verified]**

**What:** The #porkbelly command has NO admin gate. It only checks the player's display name (%name == "Super" || %name == "Jobo") and then sets %TrueClientId.adminLevel = %level to an arbitrary value taken from the command argument (%level = floor(getword(%cropped,0))). Tribes 1 display names are client-chosen and unauthenticated, so any player can rename their character to "Super" or "Jobo" and self-grant any admin level.

**Failure:** A malicious player renames their character to "Jobo", types "#porkbelly 6", and remoteSay sets their adminLevel to 6 with no password check. They now have full admin access (#ban, #kick, #addcoins, #item, #setexp, etc.), letting them wipe, dupe, or ban at will.

**Verifier:** comchat.cs:5303-5314 (#porkbelly) sets %TrueClientId.adminLevel = %level (attacker-supplied via %cropped) gated only by Client::getName(%TrueClientId) == "Super"/"Jobo", with zero password check. Contrast with the legitimate #admin handler at lines 4270-4287, which requires matching BOTH name AND a per-admin password from config/TaurikAdmins.cs ($TaurikAdmin[0] = "Jobo GNAA 20", $TaurikAdmin[1] = "Superfat krunk 15") via String::ICompare + password equality before setting adminLevel -- proving the devs already rely on passwords, not names, for real auth. connectivity.cs shows names are ordinary mutable client-chosen pilot names (it tracks a tmpname just to detect renames; no CD-key/account binding), so any player can rename to exactly "Jobo" or "Super" and type '#porkbelly 20' to self-grant arbitrary adminLevel with no password, fully bypassing the #admin gate.

### 2. $GambleBet is a single global shared across all four gambling NPCs, with no re-validation of funds at payout - lets a player collect winnings on money never actually staked
`LasVegas.cs:864` — _economy, confidence: high_ **[re-verified]**

**What:** $GambleBet[%TrueClientId] (set at LasVegas.cs:211 for carddealer bets, and again at :411 for wheelmaster bets, and :665 for quickgames bets) is keyed ONLY by clientId, not by bot/closestId, even though $state[%closestId,%TrueClientId] (used everywhere else) correctly tracks that a player can hold independent, concurrent dialogue sessions with the gambler, carddealer1, wheelmaster1, and quickgames1 NPCs at the same time (all four are separate SimGroups in KingdomKronos.mis around line 5770-5814, walkable distance apart). For blackjack (deduct immediately at bet time, :215) and highlow (deduct immediately at :237), the payout is computed LATER, in a separate chat message, by re-reading the shared $GambleBet: CardDealer_DealerPlay reads '%amt = $GambleBet[%clientId]' at line 864 to size the STAND payout, and the hl_play handler reads '%amt = $HighLowNumber...; %amt = $GambleBet[%TrueClientId]' at line 300 to size its payout. Meanwhile wheelmaster's bet-placement (line 411) and slots/roulette do NOT deduct anything - they only overwrite $GambleBet - and only deduct/pay when the player later says SPIN/roll/bet-type (line 434-435 etc).

**Failure:** Player has 100,000 coins. They bet 100 at the carddealer (blackjack), which immediately deducts 100 coins and, not getting a natural 21, enters the 'bj_play' state awaiting HIT/STAND. Without resolving that hand, the player walks to the wheelmaster NPC, picks 'wheel', and at the bet prompt types 99,900 (their entire remaining balance, which passes the affordability check since nothing has been deducted for the wheel bet yet) - this overwrites the shared $GambleBet[%clientId] to 99,900 and puts the wheelmaster session into 'wheel_play' awaiting SPIN. The player then walks back to the (still-pending) carddealer and says STAND. CardDealer_DealerPlay reads $GambleBet[%clientId] = 99,900 (the wheel's unstaked amount, not the 100 actually risked on blackjack) and, if the hand simply beats the dealer, pays out 99,900*2 = 199,800 coins - a ~199,700 coin windfall generated from a 100-coin bet. The player can then simply walk away from the still-pending, never-resolved wheel session (it is never charged since SPIN was never said), keeping the full windfall risk-free. The same technique works with highlow (line 300) or any other immediate-deduct/delayed-payout game read against a wheelmaster/quickgames bet left pending.

**Verifier:** Confirmed. $GambleBet[%TrueClientId] is set at LasVegas.cs:211 (carddealer), :411 (wheelmaster), and :665 (quickgames) — keyed only by clientId — and is NEVER cleared/reset anywhere in the codebase (grep shows zero writes of $GambleBet[...]="" ). $state, by contrast, is correctly keyed [%closestId,%TrueClientId] (comchat.cs ~10507-10567 recomputes %closestId as whichever townbot is physically nearest on every chat line), so a player can hold independent pending states with carddealer1 and wheelmaster1 simultaneously — nothing gates "one active dialogue at a time" outside the gambler bag-game's separate $GambleBot/30s-cooldown lock (lines 27-42), which does not apply to carddealer/wheelmaster/quickgames. The only guard that could interrupt this is the 10-second idle reset at comchat.cs:10641-10648 (resets $state[%closestId,%TrueClientId]="" if >=10s since last interaction with that specific bot) — but KingdomKronos.mis places carddealer1 at (-4940.81,859.54,707.498) and wheelmaster1 at (-4941.7,860.657,713.998), ~6.65 units apart (practically adjacent), so a round trip trivially completes in well under 10 seconds, never triggering that reset. CardDealer_DealerPlay (line 864: `%amt = $GambleBet[%clientId];`) then pays out 2x against whatever the shared global currently holds, and storeData has no cap/sanity check (rpgstats.cs:460, cap only applied if explicitly requested via "cap" special word, which none of these calls use). The exploit chain (bet+deduct at blackjack -> walk ~6 units to wheelmaster -> overwrite $GambleBet with a much larger unstaked amount -> walk back -> STAND) is real and produces an uncapped coin windfall.

### 9. AI::Periodic FOV targeting does a full BaseRep scan per bot every 5s (default-on), O(bots x everyone) with a filesystem probe per candidate
`ai.cs:4145` — _ai-perf, confidence: high_

**What:** With $AIsmartFOVbots defaulting to True (globals.cs:12), every enemy spawn bot's AI::Periodic (5s callbackPeriodic set at ai.cs:3791) enters the FOV branch and iterates the ENTIRE BaseRep pool via GetEveryoneIdList() (rpgfunk.cs:4950 walks all players + all bots).
